Implementation Spec

地图接入方案 · 高德 JS API 2.0

① API 版本与功能模块

  • JS API v2.0（当前最新正式版，脚本 webapi.amap.com/maps?v=2.0）
  • 底图与覆盖物：AMap.Map / Marker / Circle / Polyline / Text / OverlayGroup / Pixel
  • 实时路况：AMap.TileLayer.Traffic（autoRefresh:true, interval:180），可作为独立图层开关
  • 路况测速：AMap.Driving + policy: REAL_TRAFFIC；如有 Web 服务 Key，改用交通态势接口 /v3/traffic/status/rectangle
  • 数据校准：AMap.PlaceSearch（区域坐标）、AMap.Geocoder（地址回填）
  • 原生控件：ToolBar / Scale / MapType / HawkEye

② 地图初始化

  • 容器 #map，zoom: 11.6，center: [113.6880, 34.7620]
  • viewMode: '2D'（性能优先）、resizeEnable: true，容器尺寸变化自动重排
  • 初始化顺序：注入安全密钥 → 受控加载脚本（9s 超时）→ new AMap.Map → 建覆盖物 → 开路况图层
  • 所有实例只在 createMap() 中创建，重复调用由 mapReady 兜住，不会重复建图

③ 坐标类型

  • 统一使用 GCJ-02（火星坐标 / 国测局），数组顺序 [lng, lat]
  • Marker、Circle、Polyline、Map.center 全部是 GCJ-02；getCenter() 返回的也是 GCJ-02
  • 外部 GPS（WGS-84）或百度（BD-09）数据必须先转换，否则郑州范围内会有 300~600m 偏移
  • 已内置纯前端转换：MP.coord.wgs84ToGcj02(lng, lat)、MP.coord.bd09ToGcj02(lng, lat)，不消耗配额

④ 密钥配置方式

  • 唯一入口 window.AMAP_CFG：VERSION / KEY / SECURITY / WEB_KEY / PLUGINS
  • 安全密钥必须在脚本执行前写入 window._AMapSecurityConfig.securityJsCode，本项目在 <head> 内同步完成
  • Key 类型不可混用：JS API 走「Web端(JS API)」Key；交通态势、天气等 REST 接口需另配 WEB_KEY（Web 服务）
  • 生产环境建议改为后端代理（serviceHost）或按域名白名单下发，避免密钥暴露在前端

⑤ 关键交互逻辑

  • 点车追踪：选中车辆后每秒把地图中心对齐到车辆坐标（扣除右侧 326px 面板宽度），车始终钉在可视区正中
  • 切换目标：点另一辆车即重置追踪目标与均值窗口，速度牌随即从新车的路况重新累积
  • 手动让位：用户拖图/滚轮缩放即暂停跟随，顶部胶囊显示「已暂停」，点击恢复「跟随中」
  • 速度牌：112×124 固定盒子随 Marker 平移缩放，箭头上方显示近 120s 平均车速；只旋转 SVG，文字保持正向
  • 行驶速度：车身速度不再恒定——由弯道航向差（±400m 窗口）、司机风格、时段路况与风阻逐帧推算，加速 1.6 m/s²、制动 2.0 m/s² 限幅，始终落在 40~80 km/h
  • 图层开关：区域需求 / 车辆 / 轨迹 / 标注 / 实时路况五个 chip 独立控制覆盖物组

⑥ 异常处理与降级

  • 加载超时：9s 未就绪即判失败，切高德官方栅格瓦片直连（webrd，无需 Key），页面不白屏
  • 自动恢复：兜底后每 15s 静默重连，最多 3 次；恢复后销毁兜底并重建原生地图
  • 测速失败：4 分钟内保留上一个真实值，超时才降级为历史分时段标定；鉴权/配额类错误进入 5 分钟退避
  • 配额保护：页面切到后台暂停取数；路径规划队列繁忙时让路；取数间隔 20s、采样 5s
  • 错误可见：加载失败原因、map error 事件、测速数据源都落在「现实数据接口」面板上，便于现场排查

指标以最终实验结果为准
  • 多智能体协同相较需求热点推荐，订单完成率提升约 6.8 个百分点，主要来自对"多车同向聚集"的抑制。

MobilityPilot：面向城市出行的多智能体协同决策与动态调度系统

面向郑州市出租车运营场景，构建"环境感知 → 智能推荐 → 行为响应 → 反馈优化"的闭环调度机制。系统由天气环境、态势感知、路径规划、调度派单、司机执行五个智能体接力完成一次调度，接入高德开放平台的实时路径规划与路况数据，在动态供需下为空闲车辆推荐候客区域，并抑制多车同向聚集造成的局部运力浪费。

五个智能体

决策链
  • A0 天气环境智能体：取郑州实时天气，换算需求影响系数，作为环境输入修正 A1 需求与 A2 的 ETA。
  • A1 态势感知智能体：融合片区订单热度、实时路况、车辆 GPS 与订单流，输出区域供需缺口。
  • A2 路径规划智能体：调用高德 Driving 接口做真实路网规划，输出距离、ETA 与空驶成本。
  • A3 调度派单智能体：综合评分并做车辆-订单匹配，向司机下发派单指令与推荐路线。
  • A4 司机执行智能体：代表司机与车辆确认接单，沿规划路线行驶、送达并结算。
  • A1 → A2 → A3 → A4 首尾相接形成闭环：执行结果回写为区域权重与司机阈值，供下一轮 A1 / A3 使用。

系统模块

  • 态势总览：订单完成率、等待时间、空驶率、司机收益与区域供需缺口的实时监控。
  • 城市调度地图：郑州市主城区 18 个片区的调度地图，展示区域需求强度、车辆分布与调度轨迹回放，并标注高德接口的实时接入状态。
  • 决策图谱：以有向图呈现 5 个智能体的接力协作与各自内部步骤，支持节点下钻查看输入、输出与指标。
  • 历史数据标定：郑州本地官方口径数据定规模水平，开源逐笔行程数据定时段形状，双层标定后实时驱动仿真参数。
  • 司机智能体：不同收益偏好与接受阈值的司机 Agent 群体及其行为日志。
  • 对比实验：随机调度 / 热点推荐 / 无反馈调度 / 多智能体协同四组策略的指标对比。

技术路线

  • 仿真环境：Python 构建订单生成、车辆移动、供需状态更新与路网成本计算。
  • 现实数据接口：高德 JS API 2.0（当前最新正式版）—— AMap.Map 底图、PlaceSearch 校准片区坐标、Driving 做真实路径规划、TileLayer.Traffic 提供实时路况；测速在 Driving(REAL_TRAFFIC) 与交通态势接口之间自动择一。
  • 坐标系：全链路统一 GCJ-02，数据格式 [lng, lat]；外部 GPS(WGS-84) / 百度(BD-09) 数据经内置转换后入图。
  • 密钥与容错：Web端 Key + securityJsCode（window.AMAP_CFG 统一配置，脚本加载前注入）；加载 9s 超时自动切高德瓦片直连，并每 15s 静默重连。
  • 调度 Agent：基于 Qwen 等开源大模型，结合工具调用与结构化决策输出。
  • 工具层：需求预测、路径成本（高德 ETA）、收益评估三类可调用工具。
  • 司机 Agent：以收益敏感度、区域偏好、接受阈值刻画差异化响应。
  • 双层数据标定：郑州巡游车 11,875 台、年客运量 2.9 亿人次、网约车三期运营指标来自市交通运输局公开数据，用于定规模水平；时段强度、行程距离与速度分布来自 NYC TLC 逐笔行程记录（2024-01，271 万条），用于定形状。
  • 可视化：本页面为交互式原型，地图与图谱共享同一份仿真状态。

创新点

  • 从静态推荐到闭环决策：把"推荐对司机行为与后续供需的影响"纳入决策依据。
  • 多智能体行为交互：探索个体最优与系统整体效率之间的张力。
  • 大模型推理 + 交通仿真：形成可交互、可验证、可解释的实验平台。

数据与合规

  • 行业规模与运营指标来自郑州市交通运输局政务公开答复与《郑州市网约车市场经营风险提示》（2024-05、2025-04、2026-06 三期），均为官方公开口径。
  • 郑州未公开逐笔行程与分时订单数据，因此时段形状、行程距离与速度分布改用 NYC TLC Yellow Taxi Trip Records（2024 年 1 月，Public Domain）标定，形成「郑州定水平、开源定形状」的双层标定。
  • NYC TLC 数据为纽约市公开发布的行程记录，不含乘客身份信息；仅取其分布特征，不做个体轨迹复现。
  • 车辆位置、订单与收益等运行态数据为仿真生成，不含任何真实个人信息与轨迹。
  • 地图底图、路径规划与路况数据来自高德开放平台，符合国内地图数据合规要求。
  • 高德 Key 与安全密钥由团队自行申请，当前仅用于原型演示；正式部署将配置域名白名单，服务类请求由后端代理，避免前端明文暴露。
  • 调度区域划分为郑州市主城区 18 个片区，覆盖北至古荥与惠济、南至南四环（南环公园）与郑州植物园、东至河大郑州校区与航空港、西至郑州植物园与西流湖；各片区中心坐标按郑州真实经纬度内置（含郑州东站、郑州客运南站等枢纽节点），仅用于演示。
  • 供需口径：18 个片区的运力合计 = 100 台在线车辆，需求合计约 128，缺口控制在个位数到十几台，用于演示区域性运力偏紧与跨区调度，不代表真实营运数据。
  • 高德 API 接入：地图页左下角列出页面实际调用的 5 个高德接口——AMap.Map（底图）、TileLayer.Traffic（实时路况）、Driving（调度路径规划）、Weather（天气修正），每条接口下面还有一行实时明细：底图显示首屏耗时与当前缩放级别，路况显示下一次自动刷新的倒计时与已刷新轮次，Driving 显示成功/失败/平均耗时与行程级成功数，Weather 显示数据来源与最近更新时刻；图层面板里另有「实时路况」开关，可随时开关这张高德路况图层；面板下方是一组 实时 KPI：接口在线（N/5）、路径成功率（Driving 行程级成功率，同一 OD 被限流后自动重试仍算成功）、平均响应（高德回调平均耗时，毫秒）、60s 调用（最近一分钟的接口调用量），并附一条 近 60 秒调用分布柱图；底部汇总 累计调用、调用级成功率（每发一次请求算一次，含重试前的失败）与 P95 延迟（95% 回调的耗时上界），均按页面真实调用统计，每秒刷新；计数与计时由页面对 AMap 调用做旁路观测得到，不改变任何调用参数。
  • 追踪轨迹：点选任意车辆（点地图上的车、或用派单面板的上/下一辆）后，该车路线按实时进度分色——紫色为已驶、绿色为未驶，分界点始终贴在车头位置并随仿真每秒推进；同时其余车辆的轨迹自动压淡，避免 100 条线互相干扰。
  • 车辆追踪与实时车速：点选任意车辆后，地图立刻把该车锁定在可视区正中央（右侧调度面板会占住一部分地图，追踪点按剩余可视区居中），之后每秒随车移动保持居中，切换点另一辆车即切换追踪目标；手动拖图会暂停追踪，点顶部「跟随中」胶囊可恢复。车顶箭头按车头方向旋转，上方速度牌显示近 2 分钟平均车速——每 20 秒用 AMap.Driving · REAL_TRAFFIC 沿该车前方约 2km 做一次考虑实时路况的路径规划，以 distance / time 反推当前路况车速，每 5 秒落一个采样点，取近 120 秒的滑动均值，数字平稳不跳动；高德接口不可用时退回「历史分时段车速 × 天气 × 载客状态」估算，并在数据接口面板标注来源。速度牌字号固定为像素值，缩放地图或改窗口尺寸都不会跑位、不会被缩糊。
